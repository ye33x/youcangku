## 关键设计取舍

### 1. 三端角色分表，而不是一张 `t_account` 加 `role` 字段

- **好处**：用户、商家、管理员的字段差异很大（商家有店铺、管理员有真实姓名），分表避免大量可空字段；登录时按角色查对应表，天然不会出现「商家账号登进用户端」。
- **代价**：无法用一个外键表达「任意登录主体」。因此 `t_operation_log` 用 `operator_type + operator_id` 组合标识，而不是外键。
- **如果重来**：若需要统一登录、统一权限体系（如 RBAC 菜单），单表 + 角色表更合适。本项目按课程/毕设常见的三角色模型选分表。

### 2. 订单明细保存商品快照

`t_order_item` 冗余了 `product_name`、`product_image`、`spec`、`price`。商品改价或改名后，历史订单展示仍应保持下单时的样子，否则用户会看到「我当时明明买的是 39.9」的争议。
同理，`t_order` 冗余了 `receiver`、`receiver_phone`、`receiver_addr`，用户删改收货地址不影响历史订单。

### 3. 购物车与收藏用唯一键合并

`t_cart_item` 上 `(user_id, product_id)` 唯一，重复加购走「查询 + 累加数量」，而不是插入多行。这样购物车列表不会出现同一个商品重复条目，结算时也不必按商品聚合。
`t_favorite` 同理，避免重复收藏。

### 4. 分类删除校验

需求写明「分类下绑定有商品时，禁止删除该分类」。校验放在应用层（删除前 `count(t_product where category_id = ?)`），**不建外键**：
如果建了 `ON DELETE RESTRICT` 外键，删除失败会抛 SQL 异常，需要额外捕获翻译成业务提示；而且分类是逻辑删除，外键约束对 `deleted` 位无效。
当前 `t_product.category_id` 有外键，仅用于保证数据完整性，删除动作本身由业务层拦截并返回可读错误。

### 5. 评价与回复的「双审核」

`t_review.status` 与 `t_review_reply.status` 都是 `0待审核 / 1已通过 / 2已拒绝`。
前台查询评价必须带 `status = 1` 条件，且回复也要 `status = 1` 才展示。这样「用户评价待审核」和「商家回复待审核」两条链路互不影响，可以各自先审先过。

### 6. 日志表只写不删

`t_operation_log` 没有任何删除路径，也没有 `deleted` 字段。这是有意的：审计表一旦允许删除就失去意义。
代码层面 `AdminLogController` 只暴露 `GET`，`OperationLogService` 只暴露写入方法。

### 7. 推荐相关两张表的分工

- `t_browse_log`：原始行为，写入频繁，只追加不更新。
- `t_product_cooccur`：离线任务每天重建的共现矩阵，读多写少，(product_id, related_id) 唯一。

在线推荐只查第二张表（按主键范围 `IN` 查询），避免在请求链路里扫全量行为表。

## 主要关系

```
t_merchant 1--1 t_shop
t_merchant 1--n t_product
t_category 1--n t_product       (parent_id 自关联)
t_user     1--n t_address
t_user     1--n t_cart_item n--1 t_product
t_user     1--n t_order 1--n t_order_item
t_order    1--n t_after_sale
t_order_item 1--1 t_review 1--0..1 t_review_reply
t_user     1--n t_browse_log  n--1 t_product
```

## 索引说明

| 索引 | 用途 |
|---|---|
| `idx_product_status(status, deleted)` | 前台列表只查上架未删商品 |
| `idx_product_sales(sales_count)` | 热销榜排序 |
| `idx_order_user(user_id, status)` | 用户「我的订单」按状态筛选 |
| `idx_order_merchant(merchant_id, status)` | 商家待发货列表 |
| `idx_review_product(product_id, status)` | 商品详情页只取已通过评价 |
| `idx_browse_user(user_id, created_at)` | 按用户取行为，是推荐的主查询 |
| `uk_cooccur_pair(product_id, related_id)` | 共现查询与去重写入 |

## 演示数据

`sql/02_seed.sql` 由 `tools/gen_seed.py` 生成，包含：

- 1 个管理员（`admin`）、3 个商家（`guo_shop` / `nuts_shop` / `dried_shop`）
- 6 个用户（`user01` ~ `user06`）
- 10 个分类（4 个顶级 + 6 个子类）
- 15 个干果商品（核桃、巴旦木、开心果、葡萄干、红枣、瓜子、礼盒）
- 5 笔订单、2 条评价、18 条浏览记录
- 刻意构造了 `user01` / `user02` / `user03` 的共现关系，便于演示协同过滤效果

所有演示账号密码统一为 `123456`，密码哈希采用与后端一致的 PBKDF2 参数生成，可直接登录。
