# 推荐模块设计

推荐是本项目相对同类毕设项目的差异点，也是需求文档里唯一带「算法」字样的模块。目标不是做出工业级推荐系统，而是做到**可解释、可降级、可验证**。

## 一、为什么是「基于物品」而不是「基于用户」

需求文档写的是「通过商品共现统计实现简化版基于物品协同过滤」，这个选择是合理的：

| 维度 | 基于用户（UserCF） | 基于物品（ItemCF） |
|---|---|---|
| 相似度对象 | 用户-用户 | 物品-物品 |
| 物品多、用户多时 | 用户兴趣变化快，需频繁重算 | 物品相似度相对稳定，可离线算好 |
| 可解释性 | 只能解释为「相似用户买了 X」，用户不认识对方 | 「因为你看过 A」直接可懂 |
| 数据要求 | 需要足够多用户形成邻居 | 单用户的多个行为即可产生推荐 |

干果这类垂类商城**商品数远少于用户数增长**，且用户会重复购买同类商品，物品相似度更稳定，冷启动期也更友好。

## 二、整体流程

```
用户行为（浏览/收藏/加购/下单）
        │  写入 t_browse_log
        ▼
【离线】CooccurrenceJob  每日 03:00 全量重建
        │  按用户分组，两两配对计数（双向）
        ▼
    t_product_cooccur   (product_id, related_id, co_count)
        │
        ▼
【在线】RecommendService
   1. 取用户行为权重 → 判断走哪条策略
   2. 查共现矩阵 → ItemCfRecommender 打分
   3. 不足则用热销榜补位
   4. 为每条结果生成推荐理由
        ▼
   推荐列表（商品 + 理由 + 策略标识）
```

## 三、相似度与打分

对二值共现向量做余弦相似度：

```
sim(a, b) = co(a, b) / sqrt(N_a × N_b)

N_a = Σ_b co(a, b)     // 物品 a 在共现表中的所有共现次数之和
```

> ⚠️ **踩坑记录（已修复）**：`N_a` 必须用独立的聚合查询
> （`SELECT product_id, SUM(co_count) ... GROUP BY product_id`）得到，**不能**用「已加载的共现行求和」代替。
> 共现表是双向存储的，用户只浏览过 A 时，查询 `WHERE product_id IN (用户已看商品)` 只带回 A 的行，
> 候选商品 B 的行并没有加载，用它求和会得到 0，于是所有候选都被 `candidateTotal <= 0` 过滤掉，
> 推荐悄悄退化成「热门补位」而不报错。
> 这个问题是靠启动服务后实际调用接口、发现 `score` 全是 0 才暴露的 —— 单元测试用内存构造的对称矩阵测不出来。
> 回归用例见 `shouldScoreCandidateWhoseOwnRowWasNotLoaded`。

打分时按用户对来源物品的兴趣权重加权累加：

```
score(u, j) = Σ_{i ∈ 行为(u)} weight(u, i) × sim(i, j)
```

`weight(u, i)` 取行为次数的对数压缩：`1 + ln(count)`。
不做对数压缩的话，单个商品被反复浏览（比如反复对比价格）会主导整个推荐列表。

实现见 [`ItemCfRecommender.java`](../server/src/main/java/com/youguocang/recommend/ItemCfRecommender.java)，该类**不依赖数据库**，可直接单元测试。

## 四、冷启动三级策略

| 条件 | 策略 | 行为 |
|---|---|---|
| 无任何行为记录 | `COLD_START` | 全站或分类热销榜，理由为「全站热销第 N 名，已售 X 件」 |
| 行为商品数 < `cold-start-threshold`（默认 3） | `HYBRID` | 协同过滤结果 + 热销榜补足 |
| 协同过滤命中数 < `top-n`（行为本身充足） | `HYBRID` | 算法结果在前，热销补满 |
| 行为商品数 ≥ 阈值且命中数足够 | `ITEM_CF` | 纯协同过滤结果 |

这个阈值不是拍脑袋：当用户只有 1~2 个行为时，共现矩阵能覆盖的候选集很小，返回条数往往不足 8 条，列表会是「伪个性化」的稀疏结果，不如直接承认数据不足、用热门兜底。

另外，即便行为充足，协同过滤也可能只命中一两个商品（干果类目商品少、共现对稀疏）。
此时列表如果只返回 1 条，前端会空出大半个屏，所以同样用热销榜补满，
但策略标记仍为 `HYBRID`，理由文案也能看出哪条是算法结果、哪条是兜底。

**边界情况已处理**：如果行为充足但共现表为空（离线任务还没跑过），同样降级为 `HYBRID` 而不是返回空列表 —— 这是实际部署时最容易出问题的地方。

## 五、推荐理由（可解释性）

每条推荐都带 `reason` 与 `strategy`，前端直接展示在第一屏，答辩时也便于现场解释：

| 场景 | 理由示例 |
|---|---|
| 协同过滤 | 因为你浏览过「新疆阿克苏薄皮核桃…」，同类买家也常一起看 |
| 分类热门 | 坚果炒货分类热销第 2 名，已售 860 件 |
| 全站热门 | 全站热销第 1 名，已售 1420 件 |

关键点：`ItemCfRecommender` 在打分时同时记录**贡献最大的来源商品**（`ScoredItem.sourceProductId`）。如果没有这个字段，理由只能写成泛泛的「猜你喜欢」，可解释性就落不到具体商品上。

## 六、参数

`application.yml` → `youguocang.recommend`：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `top-n` | 8 | 每次返回条数 |
| `cold-start-threshold` | 3 | 低于该行为数走混合策略 |
| `candidate-limit` | 200 | 单次共现查询的候选上限，防止 SQL 过长 |
| `cooccur-cron` | `0 0 3 * * ?` | 离线重建时间 |

## 八、已知不足与优化方向

1. **行为去重**：当前每次浏览都插一行 `t_browse_log`，刷新页面会重复计数。建议改为「同一用户 30 分钟内同商品只记一次」，或写入时用 Redis 做去重。
2. **只用了浏览数据**：收藏、加购、下单的权重更高，应合并成加权行为。改造点集中在 `BrowseLogMapper.selectUserWeights`，可扩展为联合查询并给不同行为不同系数（如 浏览 1 / 收藏 3 / 加购 4 / 下单 5）。
3. **共现重建是 TRUNCATE + 逐条 INSERT**：演示规模够用，真实环境应改为影子表 + 原子改名，或批量 `INSERT ... VALUES (...),(...)`。
4. **没有评估**：如果要写进论文，建议补离线评估：按时间切分行为，用 `Precision@K`、`Recall@K` 和覆盖率对比「纯热门」基线。
5. **没有多样性控制**：当前只按得分排序，可能出现同一分类刷屏。可加入类目打散或 MMR 重排。
